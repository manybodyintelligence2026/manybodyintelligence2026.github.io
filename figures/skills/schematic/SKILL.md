# Scientific Schematic (`schematic`)

A schematic explains an idea, so it is judged on **correctness and clarity**, not visual clutter. Draw it with **editable vector code** (SVG, matplotlib, or TikZ), never via opaque pixel image generators that hallucinate arrows, crystal symmetries, or numbers — code can be audited, edited, and re-parameterised.

## 1. Understand Before Drawing (5-Line Plan)

Read what the physicist gave you (text, notes, README, paper) and write a 5-line plan before coding:
1. **Single takeaway:** What should a colleague grasp in 5 seconds, and **who sees it** (paper column or 16:9 slide)?
2. **Elements & relations:** List the physical objects and what acts on what (keep the list short — every extra element costs attention).
3. **Visual grammar:** Which shapes, colours, arrows, and line styles map to which physical objects (e.g., spin up/down, hopping $t$ vs. $t'$, bulk vs. boundary).
4. **Reading flow:** Left-to-right (cause -> effect, bulk -> edge, $t=0 \to t_1$) or top-to-bottom.
5. **Text budget:** At most ~12 short labels; no full sentences inside boxes.

- **Never guess unclear physics:** If a geometry, sign, ray path, chirality, or boundary condition is new or ambiguous, **ask the physicist before drawing**.

## 2. Choose the Vector Tool & Make Two Contrasting Drafts

Pick the cleanest format for the target:
- **SVG generated by Python** (fastest for the hackathon): exact coordinates from geometry formulas, zero LaTeX friction, drops straight into HTML slides and converts cleanly to PDF/PNG.
- **Matplotlib** (`patches`, `FancyArrowPatch`, `annotate`): best when the schematic sits directly next to data panels in one multi-panel figure.
- **TikZ / PGFPlots:** best when dense LaTeX equations sit inside the schematic and the team already compiles LaTeX smoothly.

Build **two genuinely different layout drafts** (`draft_a` and `draft_b`) — e.g.:
- **Draft A:** Literal / spatial geometry (real-space lattice + zoomed inset, or 3D isometric cut).
- **Draft B:** Conceptual / comparative (left-to-right mechanism steps, or before/after parameter split).

Render both drafts to PNG and open them with `render-and-look`.

## 3. Critique Like a PRB Referee

Compare both rendered PNGs honestly:
- **Clarity in 5 seconds:** Is the main mechanism obvious without reading the caption?
- **Text size (crucial):** Published schematics use **much larger text than first drafts — typically ~2x larger**. Check every subscript and label at final print/slide size; prefer direct labels on the drawing over legends.
- **Overlaps & crossings:** No arrows crossing text or each other unnecessarily; arrowheads land cleanly on targets; consistent stroke widths and arrowheads.
- **Exact physics & symmetry:** Lattice vectors, sublattices, periodic boundaries, high-symmetry points ($\Gamma, X, Y, M, K$), and flow directions must be geometrically and physically exact.
- **Colour restraint:** At most 2–3 semantic hues from the team style (Crameri / Paul Tol) plus neutral ink/grey. Colour encodes meaning, not decoration.

Pick the stronger draft, fix every critique item, and explain in one line why you chose it.

## 4. Deliver & Flag Uncertainties

- Save the code and vector output together (`code/fig_<name>.py` -> `figures/<name>.svg`, `.pdf`, and `.png`).
- Run `render-and-look` on the final PNG (max 3 rounds).
- **Explicitly state any physical details you were unsure about** so the physicist knows exactly what to double-check.
